# TYPED-INTAKE-RIO-ADAPTER-CANDIDATE-001 v0.1
# Typed Intake → RIO Adapter — Candidate Specification

**Status:** candidate proposal — docs only, no runtime change
**Version:** 0.1
**Depends on:** TYPED-INTAKE-PROFILE-001@0.1, RIO Intake Schema v1, RIO Gateway (rio-system)
**Does not change:** any runtime code, route, dependency, or deployment

---

## 1. Purpose

This document specifies the proposed boundary between the Typed Intake content-standing
evaluation layer (`language-intake-mvp`) and the RIO Governance Gateway (`rio-system`).

It defines:

- the two-plane separation between untrusted content and authenticated control;
- the invariant governing promotion from DATA to INSTRUCTION standing;
- the proposed adapter interface that would connect these two systems at a future
  runtime boundary;
- the office responsibilities of each system;
- the required failure states for the adapter;
- what must be true before any runtime implementation begins.

This document makes **no runtime claim**. Typed Intake is currently demonstrated only by
local deterministic fixtures. The RIO Gateway is live. These two systems are not presently
connected at runtime.

---

## 2. The Core Invariant

> **Untrusted content may inform a proposed action.**
> **Untrusted content may not become the authenticated task, policy, authority,
> tool target, or execution request by its own wording.**

This invariant is structural. It does not depend on whether the content contains known
injection keywords. Content cannot change its own standing by asserting it. Standing is
assigned outside the content, before the content is evaluated.

This property is locally demonstrated for TI-001 and TI-002 in `language-intake-mvp`.

## 3. Plane Separation

### 3.1 CONTENT PLANE

The content plane covers all external input arriving at the system boundary before it is
admitted as a task directive.

| Attribute | Value |
|---|---|
| Standing on arrival | `UNTRUSTED_DATA` (default for email, document, webpage, database record, tool output) |
| Standing promotion | Not permitted by content alone. Requires an independent promotion artifact through a trusted channel. |
| Governance | Typed Intake — TYPED-INTAKE-PROFILE-001@0.1 |
| Output of evaluation | PASS (DATA standing confirmed) or BLOCK (promotion denied, denial record emitted) |
| Current implementation | Local deterministic fixtures only (TI-001, TI-002) |
| Not currently running | At runtime in the live RIO Gateway |
| Authority effect | NONE on BLOCK |
| Tool calls on BLOCK | 0 attempted, 0 executed |

Content plane standing labels:

| Label | Tier | Description |
|---|---|---|
| `UNTRUSTED_DATA` | DATA | External input. Default for inbound email, documents, unverified records, webpage tool output. |
| `REFERENCE_DATA` | DATA | Trusted reference material. May inform but may not direct a task. |
| `PRIVATE_FIELD` | DATA | Sensitive data field. Subject to additional use restrictions. |

**Content plane sources that arrive as DATA:**

- External email body
- Webpage or document retrieved by a tool
- Database query output
- Third-party API response
- Tool output from an untrusted connector

### 3.2 CONTROL PLANE

The control plane covers authenticated task directives and consequential intents.

| Attribute | Value |
|---|---|
| Standing on arrival | `AUTHENTICATED_TASK` or higher |
| Source | An authenticated control path (API key, JWT, ed25519 signature) |
| Submission path | `POST /api/v1/intents` → RIO Intake Schema v1 |
| Governance | RIO Policy Engine, SPG-M (non-executing), Authorization Binding |
| Execution | Gated by Execution Gate; requires valid authorization token |
| Receipt | Generated by RIO Receipt System |
| Ledger | Written to PostgreSQL ledger |
| Settlement | Separate (not automatic on receipt) |

Control plane standing labels:

| Label | Tier | Description |
|---|---|---|
| `AUTHENTICATED_TASK` | CONTROL | Task directive from an authenticated source. |
| `POLICY` | CONTROL | Policy record from an authorized policy authority. |
| `AUTHORIZATION` | CONTROL | Authorization record from an authorized granting authority. |
| `EXECUTION_GRANT` | ENFORCEMENT | Active execution grant. Required for tool invocation. |

## 4. Threat Model

The threat this adapter boundary addresses is **standing escalation via content**:

An untrusted external input contains language that attempts to instruct the system to
treat the content as an authoritative source of task directives, policy modifications,
tool invocations, or execution requests. The attack may be embedded in any content-plane
source: an email body, a document, a database record, a webpage retrieved by a tool, or
the output of a connector.

### 4.1 Threats in scope

- Content that claims to supersede the authenticated task.
- Content that requests modification of system policy by assertion.
- Content that names a tool and requests its invocation without an execution grant.
- Content that attempts to redirect task output to an attacker-controlled endpoint.
- Content that requests `INSTRUCTION` standing by wording alone, without a promotion
  artifact.
- Payload mutation — content that is altered after its hash is bound to the intake
  envelope.

### 4.2 Threats out of scope (not claimed by this adapter)

- An attacker who supplies a valid promotion artifact through a trusted channel.
- Vulnerabilities in the model layer downstream of the intake boundary.
- Vulnerabilities in the connector layer or tool runtime.
- Side-channel or timing attacks.
- Attacks on the integrity of the verifier or fixture themselves.
- Prompt injection that does not attempt standing escalation.

## 5. Proposed Adapter Interface

The adapter is the boundary component that would connect the content plane (Typed Intake)
to the control plane (RIO Gateway). It does not currently exist at runtime.

### 5.1 Inputs

```
TypedContentEnvelope {
  envelope_id:   string              // bound identifier
  standing:      UNTRUSTED_DATA      // assigned externally, before evaluation
  source_kind:   email_body          // or synthetic_webpage_tool_output, document, etc.
  payload_hash:  sha256:<hex>        // SHA-256 of raw content bytes, bound at ingress
  permitted_uses: string[]
  prohibited_uses: string[]
  content:       string              // raw content bytes
}
```

### 5.2 Evaluation

```
TypedContentEnvelope
  → standing-preserving interpretation
  → evaluateStandingTransition(envelope)
  → PASS or BLOCK
```

On BLOCK:
- emit `TYPED_INTAKE_DENIAL_RECORD`
- `tool_calls_attempted: 0`, `tool_calls_executed: 0`
- `content_authority_effect: NONE`
- stop; do not produce a ProposedAction

On PASS (DATA standing confirmed):
- emit a `ProposedAction` — non-executing, does not have INSTRUCTION standing
- ProposedAction must be explicitly adopted by an authenticated principal before
  proceeding to the control plane

### 5.3 Non-executing ProposedAction

```
ProposedAction {
  source_ref:     envelope_id of the TypedContentEnvelope
  proposed_task:  string             // interpretation of content by trusted boundary
  proposed_scope: string
  standing:       NON_EXECUTING_PROPOSAL  // not AUTHENTICATED_TASK
  requires_adoption: true            // explicit authenticated action required
  promotion_artifact: null or <ref>  // must be non-null to request INSTRUCTION elevation
}
```

A ProposedAction is **not an intent**. It cannot be submitted directly to
`POST /api/v1/intents`. It requires explicit authenticated adoption by a verified
principal.

### 5.4 Explicit authenticated adoption

An authenticated principal (not the content, not the adapter) must review the
ProposedAction and, if appropriate, construct a new authenticated intent conforming to
RIO Intake Schema v1:

```
RIO Intake Schema v1 {
  identity:  { subject, auth_method, role, ... }
  intent:    { action, target, parameters }
  context:   { reason, risk_scope, urgency }
  authorization: null  // filled by governance pipeline
}
```

### 5.5 Outputs

```
[On BLOCK]   TYPED_INTAKE_DENIAL_RECORD → log, stop
[On PASS]    ProposedAction → authenticated adoption decision → RIO Intent (if adopted)
```

The adapter must never map arbitrary content directly into an authenticated RIO intent.
There must always be an explicit, observable adoption step between content evaluation and
intent submission.

### 5.6 Promotion flow summary

```text
TypedContentEnvelope (UNTRUSTED_DATA)
  → standing-preserving interpretation
  → non-executing ProposedAction (if PASS)
  → explicit authenticated adoption (human or authorized principal)
  → RIO Intake Schema v1 (AUTHENTICATED_TASK)
  → POST /api/v1/intents
  → governance
```

## 6. Office Boundaries

| Office | Responsibility | Boundary |
|---|---|---|
| Typed Intake | Content-standing evaluation, standing promotion refusal, denial record | language-intake-mvp → adapter boundary |
| RIO Gateway | Intent governance, authorization, execution gating, receipt, ledger | POST /api/v1/intents onward |
| SPG-M | Non-executing pattern governance, review escalation context | Before and during governance; cannot approve or execute |
| Sentinel | Future point-of-use verifier | Downstream of execution |
| MUS | Receipt and proof office | Receipt layer, ledger settlement |
| ONE | Separate system | Outside adapter scope |
| MANTIS | Separate system | Outside adapter scope |

## 7. Required Failure States

The adapter must implement all of the following failure modes:

| Failure condition | Required behavior |
|---|---|
| `standing_escalation_denied` | BLOCK, emit denial record, `content_authority_effect: NONE`, zero tool calls |
| `payload_binding_mismatch` | BLOCK with `reason_code: PAYLOAD_BINDING_MISMATCH`, treat as tampered |
| `prohibited_use_requested` | BLOCK even if no standing escalation is explicitly requested |
| `promotion_artifact_absent` | BLOCK any promotion attempt that lacks an independent promotion artifact |
| `content_claims_instruction` | BLOCK regardless of wording specifics (structural, not lexical) |
| `observed_attempt_not_from_trusted_boundary` | BLOCK; the observed_attempt must originate from a verified boundary, not the content itself |
| `adoption_step_absent` | BLOCK submission to intent API without explicit adoption record |

Fail-closed is the required default. The adapter must never silently admit a blocked
envelope by assuming the content is safe.

## 8. Non-Claims

This document does **not** claim:

1. Typed Intake is currently integrated with the live RIO Gateway.
2. The adapter described here currently exists at runtime.
3. The standing model prevents all prompt-injection attacks in production.
4. The adapter constitutes a complete security boundary (model layer, connector layer,
   and tool runtime are not in scope).
5. Content passing the intake evaluation is safe to execute without further governance.
6. ProposedAction and authenticated adoption are currently implemented.
7. A cryptographic receipt is produced for intake decisions.
8. A ledger entry is written for blocked content-plane events.
9. The full ONE/RIO/MUSS runtime is in scope for this adapter.

## 10. Implementation Prerequisites

Before any runtime adapter work may begin, all of the following must be satisfied:

1. **Typed Intake profile extended to adapter boundary.** TYPED-INTAKE-PROFILE-001
   must be extended to cover the observed_attempt sourcing requirement (§5.3), the
   ProposedAction shape, and the adoption-step invariant.

2. **Adoption step specified.** The shape, authority, and audit requirements for
   explicit authenticated adoption must be defined and reviewed before implementation.

3. **RIO Intake Schema v1 reviewed for ProposedAction compatibility.** The current
   schema requires `identity.subject` to be an agent proposing the action. The adapter
   must clarify how ProposedAction adoption maps to the existing schema without
   bypassing the identity requirement.

4. **Denial record persistence path defined.** Currently denial records are local and
   ephemeral. The adapter must specify whether denial records require ledger entries,
   and if so, through what path.

5. **Office boundary agreement.** Typed Intake, RIO, and Sentinel offices must confirm
   which components own the observed_attempt production boundary before runtime work.

## 11. Authorization Required Before Runtime Work

Any implementation that would:

- introduce a live intake endpoint that accepts external content,
- map content to an intent (even with a ProposedAction step),
- claim the adapter is operational against the live gateway,
- claim production prompt-injection protection,
- add new routes to the RIO Gateway under a typed-intake or UIF path,

must receive explicit authorization through a separate implementation proposal reviewed
against this document, TYPED-INTAKE-PROFILE-001@0.1, and the RIO Intake Schema v1.

No runtime work is authorized by this document.
